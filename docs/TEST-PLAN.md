# Test plan v2: self-healing-1 — боевой тест передачей ролей (shadow отклонён owner'ом)

Принцип: каждый провод системы тестируется НАСТОЯЩИМ действием (реальный Telegram-пейдж,
реальный Linear-тикет, реальный trigger, реальный fix→PR→auto-merge). Дубли исключаются
не «тенью», а тем, что боевая роль в каждый момент ровно у ОДНОЙ VM; откат любой роли —
одна строка (cron/systemctl), старая VM продолжает работать всё остальное время.

## Стадия 0 — prerequisites

- [ ] 0.1 PR #3: дефолт новой VM — dispatcher DRY_RUN=true + POLL off, watcher-cron
  установлен, но ВЫКЛЮЧЕН (роль передаётся явно, стадией 3)
- [ ] 0.2 Секрет `self-healing-gh-token` (интерим — токен старой VM; machine-идентичность
  до cutover)
- [ ] 0.3 `terraform plan` глазами: только новые ресурсы (имена с JOB-731), ноль
  изменений существующих
- [ ] 0.4 **Включить существующий backstop-алерт** «no meetings saved» (сейчас disabled,
  6h) на всё время теста — независимая страховка на случай ошибки нового вотчера

## Стадия 1 — Provision + воспроизводимость (день 1)

- [ ] 1.1 `terraform apply` → init без ошибок; юнит active; .env из Secret Manager
- [ ] 1.2 Claude OAuth login (документированный one-time)
- [ ] 1.3 `terraform destroy -target` инстанса → re-apply → 1.1 повторяется без ручных

## Стадия 2 — Fire drill: полный контур по-настоящему (день 1–2)

Единственный синтетический элемент — причина срабатывания; все действия реальные.

- [ ] 2.1 Owner предупреждён в Telegram («сейчас будет учебный P0»)
- [ ] 2.2 Старый dispatcher на паузе на 30 мин (`systemctl stop`) — чтобы учебный тикет
  достался новому; старый вотчер продолжает работать (боевая защита не снимается)
- [ ] 2.3 На новой VM: watcher одиночными тиками с FORCE_BAD=1 (три тика) →
  РЕАЛЬНЫЙ Telegram P0 + РЕАЛЬНЫЙ [Monitor]-тикет в Linear + РЕАЛЬНЫЙ POST /trigger
  своему dispatcher'у (DRY_RUN=false на время дрилла)
- [ ] 2.4 Новый dispatcher РЕАЛЬНО берёт тикет, расследует, находит «прод здоров»
  (жалоба синтетическая) → закрывает как не-баг с доказательствами в комментарии.
  Проверяется вся цепочка: пейдж → тикет → trigger → claim → расследование →
  Linear-мутации → [DISPATCH_RESULT]
- [ ] 2.5 Recovery-тик → реальный «RECOVERED» в Telegram; state чист
- [ ] 2.6 Все permission-denied под новым SA за дрилл собраны → роли добраны в
  terraform → re-apply (аудит SA по фактам)
- [ ] 2.7 Старый dispatcher снова запущен

## Стадия 3 — Передача роли ВОТЧЕРА (дни 2–7)

- [ ] 3.1 Одномоментно: cron-строка вотчера на старой VM выключена, на новой включена
  (LIVE: реальные пейджи/тикеты/триггеры). State-файл совместим — передача возможна
  даже посреди инцидента
- [ ] 3.2 Триггеры новой VM бьют в боевой dispatcher старой (URL параметризован в env) —
  чинит по-прежнему проверенный старый фиксер
- [ ] 3.3 Страховки на период: heartbeat dead-man (5 мин) + включённый backstop (0.4) +
  старый вотчер возвращается одной cron-строкой
- [ ] 3.4 Dead-man drill: остановить новый вотчер на 6+ мин → реальный алерт пришёл →
  вернуть → закрылся (owner предупреждён)
- [ ] 3.5 Критерий: ≥5 дней боевой работы; каждый инцидент/recovery за период отработан
  корректно (сверка с /health/output историей); ложных пейджей нет

## Стадия 3M — Передача роли ЧАСОВОГО МОНИТОРА (параллельно стадии 3)

Monitor = hourly cron: `triage.py` (детерминированный сбор ошибок: GCP Logging, Cloud
Run, LiveKit VMs, Sentry → triage-summary.json) + Claude-сессия (ТОЛЬКО Linear-дедуп,
создание [Monitor]-тикетов по эскалациям, Telegram строго из p0_alerts). Это главный
поставщик тикетов dispatcher'у — обязан быть в тесте. Зависимости на новой VM: workspace-
чекаут (lib/agent-launcher.sh, agents/claude/monitor.md — монитор запускается из
workspace, как сейчас; перенос его «дома» в этот репо — после cutover), claude OAuth,
Linear MCP конфиг, SENTRY_TOKEN из Secret Manager.

- [ ] 3M.1 Parity-тест БЕЗ side effects: `triage.py` запускается на обеих VM в один час
  (он только собирает и пишет локальный state) → diff triage-summary.json: одинаковые
  сигнатуры/severity (счётчики могут отличаться на границах окна). ≥2 успешных parity-часа
- [ ] 3M.2 Side-effect-часть под наблюдением: на новой VM один ручной прогон полной
  сессии в час, когда hourly cron старой VM ВЫКЛЮЧЕН (исключение двойных тикетов/Telegram);
  state-каталог teams/logs/monitoring скопирован со старой VM ДО прогона (иначе diff
  против пустоты ре-эскалирует старые сигнатуры)
- [ ] 3M.3 Передача роли: hourly cron off на старой, on на новой (state перенесён).
  Наблюдение за первыми 2–3 автономными сессиями: тикеты не дублируются, Telegram
  только из p0_alerts, SESSION_END маркер есть
- [ ] 3M.4 Критерий: ≥24h работы без дублей и без пропущенных эскалаций (сверка с
  latest-report.json); откат = обратный swap cron + возврат state-каталога

## Стадия 4 — Передача роли DISPATCHER (после 3.5)

- [ ] 4.1 Одномоментно: старый dispatcher `systemctl stop` (unit остаётся), новый —
  DRY_RUN=false + POLL on. Санкционированный scope не меняется: только monitor-тикеты
- [ ] 4.2 Первый реальный тикет новый dispatcher чинит под моим живым наблюдением
  (/status, /feed, логи) — готов остановить немедленно
- [ ] 4.3 Критерий: ≥2 реальных тикета доведены до терминального состояния корректно
  (fix→PR→CI→merge либо доказанный не-баг)
- [ ] 4.4 Откат в любой момент: stop новый / start старый

## Итог

После 3.5 + 3M.4 + 4.3 боевой контур ПОЛНОСТЬЮ (watcher + hourly monitor + dispatcher)
живёт на self-healing-1 и проверен реальной работой. joblander-agents продолжает нести meeting-lab и cws-кроны. Сигнал owner'а
нужен только для финальной зачистки старой VM (Фаза 4 инициативы): перенос meeting-lab,
kill-list, снос. До сигнала обе VM работают в этом устойчивом состоянии.
